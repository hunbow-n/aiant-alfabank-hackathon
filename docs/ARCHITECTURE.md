# Архитектура

## Ключевые решения

| Решение | Почему |
|---|---|
| Состояние — in-memory в одной JVM | Внешний компонент = новый источник 5xx; пара живёт секунды |
| Стор не вытесняющий | Вытеснение активной пары = провал демаскирования; при исчерпании бюджета — 429 |
| Ёмкость ограничена `Semaphore` | Прямой и дешёвый механизм, 429 не считается невалидным ответом |
| Два TTL: активная пара и tombstone | Экономия памяти и честный ответ на поздний unmask |
| Сравнение по `fingerprint` (HMAC-SHA-256) | На тексте в 100k токенов `equals` в каждом запросе недопустим |
| Детекция до критической секции + `putIfAbsent` | Корректность при 200 конкурентных соединениях без блокировок |
| Эфемерный AES-GCM ключ | Состояние живёт минуты; ротация и AAD-обвязка не нужны |
| Конфликт активного ID -> 409 | Star-маски разных значений совпадают, перезапись сломает unmask |
| Изоляция отказов на уровне детектора | Одна кривая регулярка не должна ронять запрос |
| LLM не вызывается в `/process` никогда | Реальное проксирование гарантированно ломает SLA |

## Конвейер

```text
source -> search tokens / границы полей
       -> кандидаты включённых детекторов + предпосылки combo
       -> классификация контекста и роли упоминания
       -> пороги и правила политики
       -> разрешение конфликтов на исходных диапазонах
       -> упорядоченные непересекающиеся замены
       -> однопроходная сборка + таблица токенов сессии
```

## SOLID

- SRP — детектор ищет свой тип и не знает о маскировании, сторе и HTTP.
- OCP — новый тип ПД = новый класс `Detector` + строка в конфиге.
- LSP — все детекторы возвращают кандидаты в координатах исходного текста.
- ISP — узкие интерфейсы: `Detector`, `MaskStrategy`, `SessionStore`, `SpanResolver`.
- DIP — сервис зависит от интерфейсов; внедрение только через конструктор.
